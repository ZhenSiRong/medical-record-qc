## 1. 一句话结论

| 项 | 判定 | 一句话依据 |
|---|---|---|
| **`cc_mcc_rule` 落表** | **建议做，但不单独领先交付（与 C 同批）** | 表结构（`CcMccRule`）与判读签名（`JudgeSeverity(..., rules)`）已为「换数据不改代码」做好准备，落表是纯数据搬家；但当前 `JudgeSeverity` **零生产调用方**，单独落表不产生任何可验证价值，属"表在库里、没有任何东西读它"。 |

## 2. 逐项评估

### 2.1 项一：`cc_mcc_rule` 落表

#### 现状（精确定位）

- 判读层**已按"数据可替换"写好**，只差把数据从内存挪到库里：
  - `mrs-backend/internal/service/ccmcc.go:68` `type CcMccRule struct`，字段 `DiagPrefix / Severity / Version / Source / ExcludeWhenMainPrefix / Remark` —— 与 ADR §4「版本绑定 / 严重度等级 / 排除规则留位 / 来源标注」**四要点一一对应**，可直接当表模型。
  - `mrs-backend/internal/service/ccmcc.go:137` `func JudgeSeverity(version, mainDiag string, otherCodes []string, rules []CcMccRule) CcMccJudgement` —— **规则以入参传入**，调用方（未来的 DB loader）可自行提供；判读逻辑无需改动。注释（同文件 `JudgeSeverity` 上方）明确：「将来落库为 `cc_mcc_rule` 表时字段一一对应，判读逻辑无需改动」。
  - `mrs-backend/internal/service/ccmcc.go:260` `var CcMccDemoRules = []CcMccRule{...}`，**16 条**（`TestCcMccDemoRules_TableSelfCheck` 断言 10–20 条），版本号 `CcMccDemoVersion = "demo-2026.10"`（`ccmcc.go:58`），来源恒为 `Source=demo`（`demoCcMccRule` 构造函数 `ccmcc.go:286` 在代码层兜底，内置表不可能混进 official）。
  - `CcMccJudgement.DemoOnly`（`ccmcc.go:105`）与 `CcMccDisclaimer`（`ccmcc.go:62`）——合规红线（ADR §6）已在**结果结构**里留好位。
- **表不存在**：`mrs-backend/main.go:42` 的 `AutoMigrate` 列了 **24 张表**，**无** `cc_mcc_rule`；`internal/model/` 下**无**对应模型。全文检索 `CcMccDemoRules` / `JudgeSeverity` 仅命中 `internal/service/ccmcc.go` 与 `internal/service/ccmcc_test.go` —— **零生产调用方**。
- `mrs-backend/internal/seed/icd_ext.go:73` `icd10SeverityDefs()` 已补入 CC/MCC 典型 ICD-10 编码（MCC/CC/非 CC 三档），批次 A 的"码表前置"已完成；但 `icd_ext.go` 注释明确：`sev` 字段**只用于交付统计、不落库**，落库分级归批次 B 的 `cc_mcc_rule`。

#### 依赖关系与推荐顺序

- **无前置依赖**。但**产出价值依赖 C/D**：没有调用方时，落表只是把死代码从 `.go` 挪进数据库。
- 因此**不推荐**把"落表"作为独立交付批次排在 C 前；推荐顺序：**先做 C（内存规则接线）→ 立刻伴随落表**（把 C 的数据源从 `CcMccDemoRules` 切到 DB loader）。

#### 风险与陷阱

1. **第二事实来源**：落表后，`CcMccDemoRules` **只能作为种子数据源**，判读必须统一走 DB loader；否则"库里改了、判读还用内存切片"必然漂移。建议落表时把内存切片降级为 `ccmcc_ext.go` 里的 seed 字面量，或在切片注释注明"仅种子用"。
2. **版本筛选语义必须保持**：`JudgeSeverity` 内部按 `Version` 过滤、且**空版本 = 无规则生效（fail-closed）**（`ccmcc.go` `matchCcMccRule`）。落表后调用方必须显式传"当前启用版本"，不能默认"取全部"。
3. **种子幂等键**：`SeedQcExt` 用的是 `rule_name` 判重（`handler/qc_ext.go:578`）。CC/MCC 规则无 `rule_name`，应改用 **(version, diag_prefix)** 判重（`TestCcMccDemoRules_TableSelfCheck` 已是此唯一性口径）。
4. **合规红线**：表**只存** `severity / source / version / exclude / remark`，**绝不允许**出现 groupCode / weight / 金额列（ADR §2/§6）。
5. **命名一致性**：GORM 列名由 Go 字段名推导（`diag_prefix` / `exclude_when_main_prefix` / …）；若沿用 `TestCcMccFlagFieldContract` 的思路，应加一个"列名 ↔ Save/查询口径一致"的守卫测试。

#### 验收标准（可执行）

```bash
cd mrs-backend
go build -buildvcs=false ./... && go vet ./...
go test ./... -count=1          # 含新增 loader 测试
```
- 新增测试 `TestCcMccRuleStore_LoadMatchesInMemory`：把 16 条 demo 灌库后经 loader 读出，对同一输入 `JudgeSeverity` 结果与直接喂 `CcMccDemoRules` **逐字段相等**（含 `DemoOnly=true`、`Sources=[demo]`）。
- 真库断言（复用仓库 `pgx` 驱动写一次性 `cmd`，用完即删，见 HANDOFF §7.7）：`SELECT version, source, count(*) FROM cc_mcc_rule GROUP BY 1,2` 返回 `demo-2026.10 | demo | 16`。

#### 明确的"不做"边界

- **不做**：分组码、权重、费用/金额、特例单议判定（ADR §2、§6）。表里出现任何"权重/金额"列即为越界。
- **不做**：用自造表出具支付等级判断——demo 数据必须 `Source=demo` 且对外 `DemoOnly` + `disclaimer` 双重标注（ADR §6）。

#### 依赖关系与推荐顺序

- **依赖 B（已完成）**：`other_diagnosis.go` 解析层 + `frontpage.go` 接线——**当前不阻塞**。
- **不依赖落表**：C 可直接调用 `JudgeSeverity(version, mainDiag, codes, CcMccDemoRules)`（同 `service` 包内，类型可见）。
- **不依赖官方表**（ADR §3 决定性论点：低靠/高靠是"自相矛盾检测"，不需要官方权重表）。
- **产出被 D 消费**：C 命中项即 D 弹窗的展示素材。
- **推荐顺序**：**C 先做**；落表作为 C 的"数据源切换"紧随其后（同一批次内两步）。

#### 风险与陷阱

1. **必须两条独立规则**：`mergeQcResults` 的键是 `(record_id, rule_id, field_name)`。若用**一条规则**同时产出"低靠"和"高靠"两条消息（同 `field_name`），第二条会被合并/覆盖为一条（`mergeQcResults` 同键去重，见 `qcengine.go:387` `freshByKey`）。→ **低靠 / 高靠各建一条 `qc_rule`**（不同 `rule_id`）。
2. **不得走 `conditionExpr`**：`qc_condition.go:59` `frontPageFieldString` **未映射** `other_diagnosis_flags`（也未映射 D3 新字段），写入会取空串→条件不成立→**规则静默跳过**（HANDOFF §七 / API.md §8 已知陷阱）。CC/MCC 规则应**像 `checkDiagOpMatch` 那样直接拿 `fp` 判定**，不配置 `ConditionExpr`。
3. **不得用 `OR` 表达式**：`qc_condition.go:18` `likeCondRe` 只支持单前缀 `LIKE`；写 `OR` 会退化为"恒成立"（API.md §8 陷阱 2）。本项不需要条件表达式，规避即可。
4. **必须 `WARN` 级**：ADR §8 要求"WARN 级，不拦截"。`RunQc` 仅 `ERROR` 触发 `QC_REJECTED`，故 CC/MCC 规则 `ErrorLevel` 必须为 `WARN`；否则会把合规的演示病案批量判为质控退回（回归）。
5. **`-count=1`**：`frontend/` 在 Go module 之外，Go 测试缓存不跟踪 module 外文件；凡涉及前端的验证一律 `go test ./... -count=1`（HANDOFF §七.1）。
6. **负控制**：守卫测试必须能红（HANDOFF §七.2）——构造"标记正确"的病案，确认**不误报**（ADR §10 第 2 条）。
7. **演示数据前置**：`seed.go` 首页其他诊断全空 + 前端无 flags 录入 → 需在种子补几份"已录 CC 但未标记（触发低靠）"与"已标 CC 但码不在表内/被排除（触发高靠）"的病案，否则端到端只能看到 0 命中（ADR §7）。

| 前端适配层新方法 | `frontend/js/api-store.js`（`ext` 对象内加方法） | **热点文件、串行**（唯一 API 适配层） |
| DRG 弹窗加 CC/MCC 段 / 严重度预览 | `frontend/js/components/catalog.js` | **热点文件、串行**（编目+首页摘要+质控工作台三合一） |
| 若新增独立页面/组件 | `frontend/index.html`（加 `<script>`）+ `frontend/js/components/layout.js`（`NAV`/`pageMap`） | **热点、必须串行**；否则页面加载不到 |
| 文档 | `mrs-backend/docs/API.md`（§8/§12 + 变更记录） | 与代码**同批提交**（BACKLOG 执行约定 5） |

**并行结论**：后端 severity 出口（新文件）+ 前端骨架（同一 `catalog.js` 弹窗内）可先写；`api-store.js`/`catalog.js`/`layout.js`/`index.html` 四个热点文件**必须单一所有者串行收口**（BACKLOG「热点文件」）。

#### 依赖关系与推荐顺序

- **依赖 B**（解析层 + flags 可读写）——已完成/已接线。
- **"严重度分层预览"可独立于 C**：只需 `ParseOtherDiagnoses` + `JudgeSeverity`，用内存 demo 规则即可。
- **"DRG 预检弹窗展示 CC/MCC 命中"的丰富形态依赖 C**：ADR §9 顺序为 B → C → D。
- **推荐**：D 的前端骨架可与 C 并行；**端到端联调放在 C 之后**。

#### 风险与陷阱

1. **免责声明是接口契约**（ADR §4 强约束）：任何返回严重度判断的接口，响应体**必须**带 `disclaimer`；`CcMccJudgement.Disclaimer` 已由服务层填充（`ccmcc.go:147`），handler **不要**省略或自造。
2. **demo 数据必须显著标注**：`DemoOnly=true` 时界面须显示"非官方、不得作为结算依据"（ADR §4/§6）。若只调 `JudgeSeverity` 不转述 `DemoOnly`/`Sources`，等于漏掉红线标注。
3. **DRG 弹窗当前无其他诊断上下文**：`catalog.js:185` `runDrg` 只传 `diagCode/opCode`，而 CC/MCC 判定需要 `otherDiagnosisCodes`。要"在弹窗展示命中"，需改为**传 `recordId`**（后端 `Preview` 已支持按 `recordId` 载入首页，`drg_preview.go:69`）或在编目上下文里另行取 `GET /front-pages/:recordId`。**注意**：编目阶段首页其他诊断可能尚未录入，展示会为空——需给出"未录入其他诊断"的明确文案，而非静默空白。
4. **零构建脚本顺序**：若新增组件，必须加 `index.html` `<script>` 且顺序在 `layout.js` 之前（`index.html:43`），否则 `pageMap` 取不到组件。
5. **前端契约测试**：`TestFrontendCallsResolveToRegisteredRoutes`（51 条）与 `TestApiCoverage`（94→N）**双向核对**；新增/改写接口必须同步 `API.md`，并**一律 `-count=1`**（HANDOFF §七.1）。
6. **无数据可展示**：见 2.2 陷阱 7——前端无 flags 录入、种子首页其他诊断全空。D 要能演示，先要有数据（种子或补录入 UI）。
7. **热点文件按所有权拆**（HANDOFF §七.9 / BACKLOG）：`api-store.js`/`catalog.js`/`layout.js`/`index.html` 不得由两个任务同时改。

#### 验收标准（可执行）

```bash
cd mrs-backend && go test ./... -count=1
node --check frontend/js/components/catalog.js
node --check frontend/js/api-store.js
```
断言：
- 后端 severity 接口（扩展后的 `/drg-preview` 或新端点）响应体含 **非空 `disclaimer`**；命中 demo 规则时含 `demoOnly=true` 与 `sources:["demo"]`。
- `GET /api/front-pages/:recordId` 对"已录 CC 未标记"病案，经预览接口返回逐项 `severity` 与解析层 `flag` **按位置对齐**（`CcMccItem` 与 `OtherDiagnosisItem` 同序）。
- 前端：`TestFrontendCallsResolveToRegisteredRoutes`（`-count=1`）全匹配；DRG 弹窗对"有 CC/MCC 命中"病案显示命中清单 + 红色免责块；对"未录入其他诊断"显示明确空态文案。

#### 明确的"不做"边界

- **不做**：分组码/权重/金额出具；用自造表决定支付（ADR §2/§6）。
- **不做**：特例单议判定、0000/QY 组金额折算（ADR §2）。
- **界面标注不得省略**：demo 数据不加"非官方"标注 = 违反 ADR §6 合规红线。

## 4. 首选建议

**先做批次 C（低靠/高靠接入 `qc_rule`），并把落表作为紧随其后的同一批次第二步。**

一句话理由：**C 是三项中唯一"现在做就能立即产生可验证价值"的一项**——它不需要官方表、不需要新表、解析层与判读层已成品，只需在 `qcengine.go` 的扩展分支上加两个 `WARN` 规则类型即可复用现有 `RunQc → QC_REJECTED/PASSED → 退回/整改/复核` 闭环，把 ADR §8 明确要求的"漏编 CC/MCC 是一种首页质量缺陷"真正落进现有回路；同时它产出的命中数据正是 D 需要的展示素材，落表则是把 C 的数据源从内存切到库、投入小、顺路完成。
