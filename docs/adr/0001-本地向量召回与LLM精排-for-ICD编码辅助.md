# ADR-0001：智能编码辅助采用「本地部署的向量召回 + LLM 精排」

- **状态**：已接受（Accepted）
- **决策日期**：2026-10-09
- **决策人**：项目负责人
- **取代**：`docs/BACKLOG.md` 批次 3 中「LLM 服务 = opencode zen 外部 API」的原选型（**外部 API 方案作废**，改为本地推理优先）
- **相关文档**：`docs/BACKLOG.md`（批次 3 原方案）、`SPEC.md` §2.3/§6.2、`mrs-backend/internal/handler/code_suggest.go`（现行规则版实现）

---

## 1. 背景与问题

现行「智能预编码」是**规则版**：31 条「关键词 → ICD 编码」规则（ICD-10 23 条 + ICD-9-CM-3 8 条），命中即推荐，按权重排序，编码回查 `icd_dict` 字典。实现见 `mrs-backend/internal/handler/code_suggest.go`，接口 `POST /api/code-suggest`，前端入口在编目页「智能推荐」弹窗。

它的能力边界很明确：**只认字面关键词命中，不理解语义**。病历文本写「肚子右下侧疼了三天，做手术切掉了」，规则库里的「阑尾炎」「阑尾切除」都不会命中——而这恰恰是临床病历的常见表述方式。

`docs/BACKLOG.md` 批次 3 已提出升级方向（向量召回 + LLM 精排，分三阶段），并把服务选型定为 **opencode zen 外部 API**。

## 2. 决策

**把召回层与精排层都换成「本地部署」，不使用外部 API。**

具体三层：

| 层 | 组件 | 形态 |
|---|---|---|
| **召回（Retrieval）** | **本地 embedding 模型**，对病历文本与 ICD 字典条目分别编码，向量相似度取 TopK 候选 | 本地推理服务 |
| **精排（Rerank）** | **本地生成式 LLM**，从 TopK 候选中挑出 1~3 条**推荐给编码员**，并给出理由与证据片段 | 本地推理服务 |
| **向量存储** | **本期不需要 pgvector**（见 §4.5）；演示规模（35 条码表）用 Go 内存计算余弦相似度即可 | 数据库扩展 |

> **pgvector 仅在未来规模下才需要**：原方案把 pgvector 当硬前置，实测环境不支持（见 §4.5），且当前码表只有 35 条——先用最简方案跑通，规模到了再换。

**优先级口径（本次决策的关键）：能用优先，指标后补。** 不以「先测量召回率基线」为开工前置条件；先让语义召回在本地跑通并接入界面，效果指标留待后续专项。

## 3. 刻意不做的前置工作

| 被放弃的前置项 | 理由 |
|---|---|
| 召回率基线摸底（用现有 31 条规则跑 30–50 份病案，统计正确编码是否进前 3/前 10） | 该测量**只用于判断"要不要上 LLM"**。既然已经决定上，测量的决策价值消失，等待它只会推迟开工 |
| 外部 API 与本地模型的小样本 A/B 对比 | 同上；且外部 API 方案已被本 ADR 取代 |

> **本决策接受的代价**：在语义召回上线前，我们**不知道**当前规则版的召回率是多少，因此也**无法证明**新方案相对旧方案提升了多少。这是明确接受的技术债，见 §6.1。

## 4. 为什么改用本地部署（相对原外部 API 方案）

1. **数据不出域（决定性理由）**。病案首页与病历文本含患者姓名、住院号、诊断，属敏感个人信息。外部 API 意味着把患者数据外发第三方。原方案自己在阶段 3 就把「Ollama 本地部署、数据不出域」列为终态——既然终态是本地，不如**一开始就本地**，避免"先按外部 API 的形状写一套代码、后面再改一遍"。
2. **密钥与网络依赖消失**。`.env` 里的 `OPENCODE_ZEN_*` 三个键（已配置但后端从未读过）不再是运行前置条件；演示环境不依赖外网可用性，答辩现场更稳。
3. **配额与成本不可控因素消失**。原选型是免费 flash 级模型，配额、限流、服务可用性都不由我们掌握。
4. **可复现**。本地模型版本固定，同样的输入长期给出同样的输出；外部模型可能静默变更。

### 4.5 环境实测：pgvector 当前不可用（本 ADR 的实证依据）

决策前实测了两处运行环境，**结论是 pgvector 拿不到**：

| 环境 | 实测结果 |
|---|---|
| 便携版 PostgreSQL（`tools/pg`，演示实际使用的那个） | `PostgreSQL 16.2, compiled by Visual C++ build 1937, 64-bit`；`pg_available_extensions` 中名为 `vector` 的扩展 **0 个**；已安装扩展仅 `[plpgsql]` → `CREATE EXTENSION vector` 不可用 |
| Docker 形态（`docker-compose.yml` 用的 `postgres:16-alpine`） | 该镜像不含 pgvector；且**当前机器 PATH 中无 docker**，无法改用 `pgvector/pgvector:pg16` 验证 |

**对本决策的影响**：pgvector 从"硬前置"降级为**规模驱动项**。理由：

- 当前码表只有 **ICD-10 24 条 + ICD-9-CM-3 11 条 = 35 条**，向量召回在 Go 里直接算余弦相似度就是**微秒级**，引入向量索引没有收益
- 全量国标码表（数万条）才是 pgvector 的适用场景；那属于"换真实码表"之后的规模问题

**因此本期推荐路径**：embedding 向量先随 `icd_dict` 落库（数组/JSONB 列或独立小表均可），相似度在应用层计算；**当码表规模或延迟真正成为瓶颈时，再引入 pgvector**（届时优先走 Docker 镜像 `pgvector/pgvector:pg16`，或为便携版手工装扩展）。这条路径不阻塞开工，也不需要在演示机器上折腾数据库扩展。

## 5. 不变量（本决策不改变的原则）

**本产品的定位是「模型辅助编码」——即推荐，不是「模型直接编码」。**

模型产出的是**建议**：候选编码 + 理由 + 证据片段。**决定权与责任始终在编码员**。这不是"技术上做不到自动编码所以退而求其次"，而是**刻意的职责划分**：

- **合规依据**：国家病案质量与编码管理规范要求编码员依据病案内容自主判断并**承担编码责任**。
- **支付后果**：病案首页编码直接关联 DRG/DIP 支付，编码错误导致拒付，责任必须可归属到人。
- **行业实证**：可解释性是医疗机构采纳 AI 编码的**硬前提**（见 `docs/BACKLOG.md` 引用中山八院/哈工大「智码系统」：显式呈现编码证据片段）。

因此架构上保持：

- 模型输出限于"候选 + 理由 + 证据片段"，**不落库、不自动填入**
- **必须由编码员点击确认才填入表单**——这一条是产品边界的落地点
- 最终编码**必须**回查 `icd_dict`（沿用既有 `CODE_EXIST` 机制），字典里没有的编码一律不采纳
- "从候选清单里选"是**实现手段**（它同时消除了幻觉风险），**产品定位是"推荐给编码员"**——两者不要倒过来理解

现行 `code_suggest.go` 文件头已写明这一定位，前端「智能推荐」的交互（点击候选才填入）也已经是这个形状——**本次升级不改这两点**，只把"候选从哪来"从关键词命中升级为语义召回。

## 6. 后果

### 6.1 负面后果（明确接受）

| 后果 | 说明 |
|---|---|
| **缺少效果基线，改进幅度不可证明** | 未做召回率摸底；上线后无法回答"比规则版好多少"，除非后续补测 |
| 本地推理的**延迟与硬件成本**由我们承担 | 取决于演示机器；需实测单次推荐耗时，必要时限制 TopK 与输出长度 |
| 需要**模型分发与版本固定** | 模型权重（数百 MB 到数 GB）如何随项目交付/首次运行下载，需在实现时定 |
| **部署复杂度上升** | 多一个本地推理服务进程；`tools/demo-start.cmd` 需相应扩展或提供降级路径 |

### 6.2 必须提供的降级路径（硬要求）

**本地推理服务不可用时，必须自动回落到现行规则版（31 条关键词规则）。**

理由：演示现场不能因为推理服务没起来就整个「智能推荐」不可用。回落时界面应明确提示"当前为规则版推荐"，不伪装成语义推荐结果。

### 6.3 对既有文档的影响

- `docs/BACKLOG.md` 批次 3：服务选型表与三阶段划分需按本 ADR 重写（去掉 opencode zen 外部 API，阶段划分改为"本地召回 + 本地精排 + 降级路径"）
- `SPEC.md` §2.3「明确不做」与 §6.2「后续演进」现在把"真实 LLM 智能编码"列为不做/后续，与"已决定开做"矛盾，**需同步修正口径**
- `.env` 中的 `OPENCODE_ZEN_*` 三个键成为**无用配置**，需决定删除或保留备用

## 7. 考虑过的替代方案

| 方案 | 未采用的原因 |
|---|---|
| **保持规则版，不升级** | 无法处理"临床自然语言表述"这一主要场景，需求匹配度矩阵中该项仍为缺失 |
| **外部 LLM API（原 opencode zen 方案）** | 患者数据出域；且终态本就是本地部署，先外部后本地等于写两遍 |
| **只做向量召回、不做 LLM 精排** | 召回只能给相似度排序，无法给出**证据片段与理由**。可解释性是行业采纳的硬前提（见 `docs/BACKLOG.md` 引用中山八院/哈工大「智码系统」案例：显式呈现编码证据片段） |
| **只做 LLM 精排、不做向量召回** | 精排是**重排**，它无法召回候选之外的东西；瓶颈在召回层时精排无能为力。这也是原方案把它排在阶段 1 仅作过渡的原因 |
| 引入独立向量库（Milvus / Qdrant） | 现有 PostgreSQL 加 pgvector 扩展即可，不新增组件与运维面（遵循"用原生平台能力优先"） |

## 8. 待定的实现细节（本 ADR 不锁定，实现时定）

以下是**实现层选型**，不影响本决策的成立，留到开工时再定：

1. **embedding 模型具体型号**：中文医学语料表现、体积、是否需 GPU 推理
2. **本地推理服务形态**：Ollama 或其它；需同时提供 embedding 接口与 chat 接口
3. **精排模型的上下文与提示词设计**：如何把 TopK 候选与病历文本一起喂入，如何约束输出为"只选不生成"
4. **ICD 字典向量化的时机**：启动时全量、还是随 `icd-dicts/import` 增量
5. **TopK 取值与相似度阈值**（影响延迟与召回宽度）
6. **向量落库形态**（见 §4.5）：数组列 / JSONB / 独立小表；以及**何时**升级到 pgvector（触发条件建议：码表规模进入千级或单次召回延迟超阈值）

## 9. 后续验证（指标补测，不阻塞开工）

开工后、有时间时补做，用于回答"到底好了多少"：

1. 召回率基线：构造带标准答案的病案文本集，统计正确编码是否落在 Top3 / Top10
2. 精排增益：对比"仅召回"与"召回 + 精排"的正确率
3. 延迟：单次推荐端到端耗时（P50 / P95）

> 补测的价值在于：若召回率已高而精排增益有限，可考虑关掉精排以降延迟；若召回率低，则应优先换 embedding 模型而不是调提示词。

## 10. 已被本 ADR 推翻的原方案假设（避免后来人误读）

| 原方案假设 | 现状 |
|---|---|
| LLM 走外部 API（opencode zen） | ❌ 作废——改本地部署，理由见 §4 |
| 分三阶段（阶段 1 外部 API 精排 → 阶段 2 加向量 → 阶段 3 本地化） | ❌ 作废——直接做本地召回 + 本地精排，不分"先外部后本地"的阶段 |
| pgvector 是必需组件 | ⚠️ 降级——实测环境拿不到（§4.5），且当前规模不需要；改为规模驱动项 |
| embedding 模型定为 Qwen3-Embedding | ⚠️ 待重新评估——原依据是外部评测结论，本地部署需重新权衡体积与推理硬件 |
