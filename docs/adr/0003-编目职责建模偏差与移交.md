## 1. 背景

编目（ICD 编码）是本系统的核心作业。用户在对界面做验收时提出疑问：

> "我很疑惑编目这个流程是谁去做，参考什么去做？"

追问后发现：**状态机实现是对的，但职责建模有三处与行业规范不符**。本文档记录这三处偏差、依据、影响与修复选项。

## 2. 行业事实（依据 `docs/research/A1`，非推测）

| 问题 | 事实 | 出处 |
|---|---|---|
| **谁编目** | 病案科（病案室/病案统计科）的专职**疾病编码员**，配置 6–8 人 | A1:19 |
| **参考什么** | ① 病历正文（病程、手术记录）② **临床医师已填好的首页** ③ ICD 编码规则 | A1:19、A1:63 |
| **工作量** | 日均 44–56 份/人，约 **10 分钟一份** | A1:39、A1:40 |
| **首页第一责任人** | **临床医师**。规范明确**编码员不能凭空添加/修改诊断**，发现问题只能**退回** | A1:160 |
| **完整链路** | 护士整理 → **医生写病程/首页** → 主治审核 → 质控抽查 → **病案科编码** → 终末质控（共约 6 次经手） | A1:63 |
| **岗位编制实例** | 眉山市人民医院：科主任 1、**编码员 6**、**首页质控员 1**、统计员 1、管理员 5 | A1:32 |

**要点**：编码发生在**临床医师填完首页之后**；编码员的职责是把临床诊断**"翻译"成 ICD 码**，而不是决定诊断本身。

## 3. 已实现且符合规范的部分（不要改）

- 病案必须先回收（`RECYCLED`）才进待编目队列——对应"出院回收 → 编码"
- 编码员 = 病案室（`POST /catalogs` 为 ADMIN only）
- 编码**强制回查字典**（必须存在于 `icd_dict`），对应"编码存在性校验"
- 编目人员**只读**取当前登录人（`catalog.js` 的只读 input + 后端 `coderName` 取 JWT 用户名），不是可选下拉
- 归档后禁止再编目（409 锁定，依据 E9）

## 4. 三处偏差（本文档的核心）

### 偏差 1：「主要诊断」由编码员选定

**现状**：编目表单的主诊断字段是 **`主要诊断 · ICD-10 编码` + 编码选择器**（`frontend/js/components/catalog.js`，编目工作台）。
**后果**：**选码 = 定主诊断**。主要诊断直接决定 DRG 入组与支付，等于让编码员决定诊断与收入归属。

**与规范的冲突**：主要诊断应由**临床医师**判断（A1:160）。且 A1:163 指出这正是合规风险来源——病案科按 ICD 技术标准判"编码误差"、医保科按基金支付判定，**同一件事可能被认定为"高套编码/虚假结算"**。

**正确形态**：诊断**名称**由医生定（编码员只读）→ 编码员为该诊断**选码**。两件事应分开。

### 偏差 2：医生填写的首页字段被「编目动作链」代写

**现状**：`frontend/js/api-store.js` 的编目动作链在 `PUT /front-pages/:id` 时写入：

```js
admitDiagnosis:  patch.diagMain + '待查',   // 入院诊断
dischargeDiagnosis: patch.diagMain,         // 出院诊断
actualDays: rec.stayDays, totalCost: ...
```

同样的写法也出现在种子：`mrs-backend/internal/seed/seed.go:340`
`AdmitDiagnosis: m.def.name + "待查", DischargeDiagnosis: m.def.name`。

**后果**：`GET /api/front-pages/:id` 返回的"入院诊断/出院诊断"**看起来像医生填写的原始数据，实际是编码动作的产物**。因此：

- **质控规则若校验这些字段，校的是自己的产物，而不是医生的填写**
- 入院诊断被硬编码加上"待查"后缀，是系统编造的内容

**依据**：`AdmitDiagnosis` / `DischargeDiagnosis` 属首页数据元，第一责任人是临床医师（A1:160）。

### 偏差 3：编码员与质控员未分岗

**现状**：`sys_role` 只有两个角色（`ADMIN 病案管理员` / `DEPT_USER 科室用户`）。**「编码员」与「首页质控员」都是 `ADMIN`**。

**后果**：

- 系统无法回答"这份病案是谁编的目"——演示库里 `catalog_entry.coder_name` 全是同一个账号（admin 的真人名"王主任"），而王主任在角色定位上是**病案管理员/科主任**，不是编码员
- **质控退回返修闭环的独立性不成立**：同一个账号自己编目、自己退回、自己复核

**依据**：A1:19/20 与 A1:32 显示这是两个独立岗位（编码员 6–8 人、首页质控员 1–2 人）。

## 5. 决策

**本批次不改代码。** 三处偏差记为**已知边界**，并在交接文档中作为待办移交。

**理由**：

1. 三处都涉及**职责建模**，不是字段级修补——尤其偏差 1 与 3 会改动编目契约、角色模型、路由分权与前端多处
2. 项目进入**移交阶段**，由接手人统一评估优先级与排期，比在当前批次仓促改更稳妥
3. 偏差 2 虽是数据真实性问题（影响质控可信度），但它**不阻塞演示**，且修法明确（见 §6 选项 A/B），交付给接手人成本很低
4. 如实记录并说明边界，**优于**留下"看起来做了、实际没做全"的假象——这与 ADR-0002 §3 的既定原则一致：**凡依赖外部口径或需要组织结构支撑的部分，不做假实现，只做能在自家数据上完成的判断**

## 6. 修复方案选项（供接手人选择，本 ADR 不锁定）

| 档 | 内容 | 影响面 | 备注 |
|---|---|---|---|
| **A** | 只修偏差 2（编目动作链不再代写 `admitDiagnosis`/`dischargeDiagnosis`；医生字段缺失时**留空并提示**，而不是编造"待查"） | 小：`api-store.js` 载荷 + 种子 + 首页字段口径说明 | **建议优先**，因为它是数据真实性问题，且成本最低 |
| **B** | A + 拆分"诊断名称"与"编码"两个输入：主诊断名称由医生填写（编码员只读），编码员为其选 ICD 码 | 中：编目表单、`POST /catalogs` 契约、首页字段归属 | 需明确"医生未填时编码员能否继续" |
| **C** | B + 拆出「编码员 / 首页质控员」两个角色：编码员只能编目，质控员才能退回/复核 | 大：角色模型、路由分权、前端多处、演示数据 | **退回返修闭环的独立性只有做到这一档才真正成立** |

**推荐路径**：**A 先做**（低成本、修数据真实性）→ **C 记为演进项**（组织建模，取决于交付范围）。

**注意**：C 与 ADR-0002 的严重度预警有耦合——CC/MCC 漏编提示若走质控闭环，其"退回/复核"的独立性同样受偏差 3 影响。

## 7. 已知的连带口径问题（一并移交，非本 ADR 引入）

1. **数据隔离未生效**：`middleware/cors.go:25` 自述"参考 `sys_role.data_scope`（ALL/DEPT），**当前骨架仅做功能角色校验**"。实测 `deptuser` 调 `/records/page` 可见**全院 87 份**病案。已在 `SPEC.md` §2.3 与 `API.md` 待确认事项中记录。
2. **队列与详情诊断显示不一致**：待编目队列取 `r.diagMain`（=`fp.dischargeDiagnosis`），患者信息栏取 `form.icdName`；表单被切换选项时两处不一致（属显示口径问题，非数据错误）。已在验收中发现。
3. **首页/结算口径的用户可见说明**：编码与主要诊断的职责边界应写进面向用户的说明（`docs/extension-guide.html` 已按"编码辅助"口径标注，但未覆盖"谁定主诊断"）。

## 8. 后续验证（接手人做修复时的验收口径）

1. 偏差 2 修复后：`GET /api/front-pages/:id` 的 `admitDiagnosis`/`dischargeDiagnosis` 应来自医生填写路径；编码动作**不得**改写它们
2. 质控规则不得校验由编码动作产生的字段（否则是自校验）
3. 若做 C：`catalog_entry.coder_name` 应能区分编码员；退回/复核的操作人不应与编目人恒等
