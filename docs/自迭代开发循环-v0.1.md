# 自迭代开发循环 · v0.1

> 2026-10-16 · 状态：**命名与方向已拍板**（四项决策见 §6.0）· 进入试运行；跑完一个批次后复盘定稿 v0.2。
> 定位：把我们已经跑出来的「少指令 + 自迭代 + 专家节拍」实践收束成可复用骨架。
> 关联：`docs/HANDOFF.md`、`docs/BACKLOG.md`、`docs/adr/`、`mrs-backend/features/README.md`、`docs/专家评审包/`（评审包与回执归档）

## 0. 一句话

**用户只投意图 → 环自动流转 → 磁盘记住状态 → 门禁判机器对错 → 医疗业务专家按节拍校准业务方向。**

## 1. 问题与既有雏形

三个痛点：

1. **指令一多就缠斗**：指令越下沉到实现层，返工与验证成本越高（PowerShell 5.1→7.6 的环境拉锯，就是「噪声吃掉迭代带宽」的样本）。
2. **迭代靠人推**：人一天不推，环就停；重启后要重新热身。
3. **正确性只有机器信号**：`go test` 全绿 ≠ 业务正确——「状态机是否符合真实病案室流程」「CC/MCC 口径是否临床成立」，机器判不了。

既有雏形（本项目已经长出来的部分）：

- 状态工件：`HANDOFF.md` / `memory/` / `BACKLOG.md` / `docs/adr/` / `features/*.feature`
- 门禁组合：build / vet / test `-count=1` / gofmt / 契约覆盖 94/94 / BDD / sentrux
- 并行所有权：多 agent 按文件所有权切分（批次 B 验证过）
- 负控制纪律：不能红的测试等于没写
- AI 预评审：`docs/adr/0002-批次C-D与落表评估.md`
- 一屏汇报：状态表 + 证据 + 下一步

## 2. 抽象模式（与领域无关的部分）

### 2.1 定义

一个由**意图**驱动、由**缺口表**排序、由**双层验证**把关（机器门禁 + 领域专家）、由**磁盘工件**记忆、可**断点续跑**的开发环。

### 2.2 角色

| 角色 | 谁 | 核心职责 | 纪律 |
|---|---|---|---|
| 意图源 | 用户 | 投放目标级意图；拍板方向 | 只说目标，不下沉实现细节 |
| 主控 | 主 agent（会话负责人） | 读状态 → 选缺口 → 分派 → 集成 → 固化 → 汇报 | 状态外置；证据制；保持为「最少的串行单点」 |
| 施工单元 | 子 agent（按文件所有权） | 执行变更 + 自证 | 不越界；负控制；回传证据原文 |
| 领域专家 | 医疗业务专家（通道参数化，见 §3.5） | 按节拍校准业务正确性 | 只审业务；发现必须可转译 |
| 门禁 | 构建 / 测试 / 契约 / 结构工具 | 输出红绿信号 | `-count=1`；可证伪 |
| 状态工件 | 磁盘文档 | 承载「继续」的解析基础 | 先写盘，后汇报 |

### 2.3 六拍环

| 拍 | 谁 | 动作 | 产出 | 铁律 |
|---|---|---|---|---|
| ① 读状态 | 主控 | 读磁盘工件，重建「我在哪、有什么坑」 | 可续跑的上下文 | 凡要跨会话记住的，必须写在磁盘上 |
| ② 选缺口 | 主控 | 从缺口表按「价值 × 紧迫度」排序取头部 | 本批任务单（含不做的边界） | 优先「立即产生可验证价值」的项 |
| ③ 并行施工 | 施工单元 | 按文件所有权切分任务，互不重叠 | 变更 + 负控制自证证据 | 不共享文件的并行，才是真并行 |
| ④ 门禁验证 | 机器门禁 + 主控 | 全量门禁跑分；交叉复核各方证据 | 红 / 绿信号（可证伪） | 不能红的测试等于没写 |
| ⑤ 专家节拍 | 医疗业务专家 | 里程碑时提交评审包，收回结构化发现 | 转译成下一迭代的输入 | 只审业务正确性；按节拍介入，不随叫随到 |
| ⑥ 固化汇报 | 主控 | 先写盘：记忆 / ADR / 交接 / 缺口表 | 一屏汇报 + 等下一个意图 | 先固化，后汇报——否则「继续」无从解析 |

环从 ① 依次走到 ⑥，再回到 ①。用户的一个「继续」在 ① 被解析成具体工作。

### 2.4 三条不变量

1. **状态在磁盘**——凡是要跨会话存在的东西，必须写盘（人脑与模型上下文都不算存储）。
2. **证据在门口**——任何「完成」都必须能指到可复核的输出（原始输出、哈希、截图）。
3. **专家在节拍上**——专家按里程碑介入：不随叫随到，也不缺席。

### 2.5 少指令的机制

1. **状态外置** → 「继续」可以被解析成具体工作。
2. **意图展开规则**：目标 → 缺口 → 任务；展开有歧义时**给选项**，不闷头猜。
3. **升级策略（何时必须停）**：不可逆操作 / 领域歧义 / 需要凭据 / 方向分叉 → 停下来问；其余 → 先做。
4. **汇报收敛**：一屏（结论 + 证据 + 下一步），细节都在工件里。

### 2.6 自迭代的机制

1. **缺口驱动**：环的输入恒为「排序后的缺口表头部」，不靠人推。
2. **失败自喂**：红灯、返工、负控制结果 → 自动成为下一迭代输入。
3. **教训沉淀**：每次试错 → 记忆 / ADR / 惯例，下次不重犯。
4. **节拍约束**：自主 ≠ 无限狂奔——专家节拍 + 升级策略是护栏；每批次一个收敛点。
5. **环自迭代（元层）**：每跑完一个批次 → 复盘 → 修订本模式文档（v0.x 递增）。

### 2.7 反模式

| 反模式 | 后果 | 对策 |
|---|---|---|
| 无状态迭代（会话级记忆） | 「继续」失效，每次都重新热身 | 状态工件 + 先固化后汇报 |
| 无负控制的验证 | 假绿灯，测了等于没测 | 负控制铁律 |
| 专家意见不转译 | 评审变聊天，问题原样复发 | 转译铁律（§3.3） |
| 并行无所有权 | 文件冲突、互相覆盖 | 派发前先出「文件所有权清单」 |
| 无边界的自主 | 方向性事故 | 升级策略 + 节拍约束 |
| 指令下沉到实现层 | 绕开排序与验证，缠斗回归 | 意图源只说目标 |

## 3. 专家接入层（医疗业务专家）

### 3.1 三类介入

| 方式 | 场景 | 形式 | 节拍 |
|---|---|---|---|
| 文档评审 | 批量业务规则 / 流程 | 异步：评审包 → 结构化发现 | 里程碑（批次级） |
| 决策问询 | 单点领域歧义 | 快问快答：一组问题 → 裁定写 ADR | 触发性 |
| 验收走查 | 演示动线 / 界面叙事 | 同步走查：8 分钟动线复盘 | 阶段收口 |

### 3.2 评审包五件套（模板）

① 评审对象（界面 / 流程 / 字段 / 规则，带截图）
② 针对性问题（≤7 条）
③ 我方现状与已知取舍（诚实标注「可能不对的地方」）
④ 期望输出格式（发现 / 依据 / 严重度 / 建议）
⑤ 边界声明（不需要审什么：代码实现、性能）

示例（CC/MCC 口径评审——**首轮试跑对象**；实际送审包见 `docs/专家评审包/批次C-CC-MCC口径-评审包-v1.md`）：

- 对象：ADR-0002 §4/§5 规则表 + 16 条演示判读表 + 批次 C 低靠 / 高靠检测设计
- 问题：演示表严重度划分是否临床成立？排除形态是否成立？两条 WARN 规则是否妥？降噪情形有哪些？
- 现状：16 条 Source=demo 规则，不用于支付（合规红线），仅作预警
- 期望格式：发现 ／ 依据（惯例或文件出处） ／ 严重度（阻断 / 应改 / 建议） ／ 建议动作
- 边界：不审代码实现与性能；不出具分组码 / 权重 / 金额

### 3.3 转译铁律（本模式的核心纪律）

**每条专家发现，必须落成「Gherkin 场景 ｜ 质控规则 ｜ ADR 决策 ｜ 缺口表条目」之一；否则视为未处理。**

| 发现类型 | 转译为 | 落点 |
|---|---|---|
| 业务规则与实现不符 | Gherkin 场景（可执行断言） | `features/*.feature` |
| 判定口径需调整 | 规则 / 阈值 / 判定表 | `qc_rule`、`drg_rules`、ADR |
| 边界与合规要求 | ADR 决策 + 「不做」清单 | `docs/adr/` |
| 暂无法执行的建议 | 缺口表条目（带触发条件） | `BACKLOG.md` |

### 3.4 混合节拍：AI 预评审 + 真人终审

- **AI 预评审**（常驻、每迭代）：用专家人格 / 预评审文档过滤低级问题（已实践：agent-eval 评估文档）。
- **真人终审**（按批次）：把专家时间花在刀刃上——只审 AI 预评审消化不了的业务判断。
- 两者产出走**同一条转译铁律**。

### 3.5 专家通道（已拍板 2026-10-16）

**MedWork 是什么**（用户确证）：MedWork 是**接入了京医千询大模型的垂直领域 Agent 助手**。定位：专家池的**远期通道**——「循环建起来之后，引入它的评审会让我们的测试/评分变得更专业」（用户原话）。

**专家池参数化（三插槽）**：

| 插槽 | 通道 | 状态 |
|---|---|---|
| 常规评审 | 市场专家中心（对口候选：傅医保 · DRG/DIP 与病案编码质量；田老师 · 医院质管与信息化） | **本轮启用 1 位试跑**（先单个，不铺开） |
| 终审 | 真人专家（团队 / 合作） | 评审包通道已就绪，待接入 |
| 远期 | MedWork（京医千询基座） | 循环试跑稳定后接入；接入时按 §3.2 评审包格式喂料 |

**本轮策略**：先由**单个**专家跑通「评审包 → 结构化发现 → 转译落盘」全链路，验证后再谈扩容与 MedWork 接入；不要一次引入多源专家（发现不可归因，元评审基线无法建立）。

### 3.6 元评审：怎么评审「专家的评审质量」（v0.1 议题）

用户点名方向（2026-10-16）：**「怎么正确评审专家的评审质量」是继续深入的议题。**

v0.1 立场：**专家评审本身就是环上的一个被测组件——对组件就要有验收标准。** 五个机制雏形（先记录，试跑中用数据校准）：

| # | 机制 | 做法 | 防什么 |
|---|---|---|---|
| 1 | **种子缺陷回灌** | 送审材料里预埋若干已知的领域错误（如：故意写错的严重度判定 / 排除项），看专家是否捕获；未捕获的种子 = 该轮评审的盲区标尺 | 评审走过场 |
| 2 | **转译率** | 每条发现必须落成 Gherkin / 规则 / ADR / 缺口表之一（§3.3 铁律）；无法落盘的条目计为「空话率」 | 评审变聊天 |
| 3 | **可反驳性（引证）** | 每条发现要求给依据（编码规则 / 教材 / 官方文件条款）；无引证的发现降权处理 | 玄学意见 |
| 4 | **一致性** | 同一材料两次送审（或两位专家交叉）看高价值发现的重合度；两次都出现的才当硬结论 | 单次评审的偶然性 |
| 5 | **结果回填** | 转译条目进入工程实现后，用门禁与真实使用结果回填专家评分卡（捕获率 / 误报 / 可执行性） | 评审与结果脱钩 |

**边界**：元评审自身不做无限套娃（「评审的评审的评审」）——锚在**可执行证据**（种子缺陷、落盘条目、门禁结果）上，不引入新一层专家。

## 5. 定名（已拍板 2026-10-16）

**自迭代开发循环**（Self-Iterating Development Loop，SIDL）。
