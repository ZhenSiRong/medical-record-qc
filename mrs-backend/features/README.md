# features/ —— 行为规范（可执行）

本目录存放 **Gherkin `.feature` 文件**：把项目已定稿的行为规则翻译成机器可跑的场景。
由 `internal/bdd` 的 godog 套件驱动，**随 `go test ./... -count=1` 一起执行**，不额外引入命令行工具。

## 权威层级（改之前先读）

本目录**不定义业务规则**，只做引用。三者的关系是单向的：

| 层级 | 文件 | 地位 |
|---|---|---|
| 领域行为（状态机） | `SPEC.md` §2.2「三条状态机」 | **权威源** |
| 接口行为（契约） | `mrs-backend/docs/API.md` | **权威源** |
| 可执行场景 | 本目录 `*.feature` | **只做引用**，冲突时以权威源为准并修正本目录 |

每个 `.feature` 文件头部都写明了它引用的权威源章节与行文范围。新增场景时请照此格式补充。

## 运行

```bash
cd mrs-backend
go test ./internal/bdd/ -count=1 -v
```

- `-count=1` **不可省**：`frontend/` 在 Go module 之外，测试缓存不跟踪其变化，不加会得到假绿灯。
- 只看场景清单（不跑）可读 `.feature` 原文；文件中「Scenario」即一条可独立验收的行为。

## 断言层级与「无数据库桩」

当前场景统一在 **HTTP 层**断言，挂载**真实全量路由树**（含真实中间件链：
CORS → OperLog → Auth → RequireRole），但 **db=nil 不连库**。由此：

- 400 / 401 / 403 这类「碰库之前就该拒绝」的行为 → 可在无库环境断言；
- 合法请求越过校验后会撞上 `h.DB` 并 panic，被测试装配的静默 Recovery 兑现为 **500**。
  这个 **500 不是缺陷**，而是「校验已放行」的证据。

因此本层是**自足（hermetic）**的：不需要 PostgreSQL、不需要启动应用进程、不需要 Redis。

## 为什么是 godog（而不是 pytest-bdd）

因为本项目的测试门禁是 `go test ./... -count=1`。用 godog 可让行为场景留在**同一条门禁**内，
不新增语言、工具链与 CI 环节，并直接复用 `router.Register`、`middleware.SignToken` 等既有基建。

**Gherkin 与 runner 是解耦的**：将来若需要「活服务 + 真库」的黑盒验收层，可以另起
pytest-bdd 或 behave **引用同一批 `.feature` 文件**，无需重写场景。注意那条路是非自足的
（需要 PostgreSQL 与应用进程在线；本仓库无 sqlite 驱动，纯内存跑不了）。

## 写作约定

1. **步骤停留在领域/接口层**，不要写 UI 动作。
   反例：`When 我点击「保存」按钮` —— 前端为零构建形态且无浏览器驱动，这种步骤落不了地。
   正例：`When 以其他诊断编码 "..." 与严重度标记 "..." 保存病案首页`。
2. **一条 Scenario = 一条可独立验收的行为**，Scenario 名用陈述句写清「预期会发生什么」。
3. **拒绝类行为要同时断言状态码与原因**（`Then 响应状态码应为 400` + `And 响应应说明 "..."`），
   只断言状态码会在「拒绝的理由变了」时静默放过。
4. 新增场景后按项目纪律做**负控制**：故意破坏对应实现，确认该场景**变红且精确指位**，
   再逐字节还原（附 sha256 佐证）。
